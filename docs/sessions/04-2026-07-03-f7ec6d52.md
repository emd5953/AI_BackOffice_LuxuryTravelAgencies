### 🤖 **Claude** · 01:51

These are explanation questions, not a new implementation task — answering directly, no plan changes needed.

**1. What's Drizzle?**
A TypeScript ORM (object–relational mapper). `src/db/schema.ts` defines your tables *in TypeScript*, and Drizzle gives you two things from that single source of truth:

- **Typed queries**: `db.select().from(clients)` returns `Client[]` with real types — typo a column name and the compiler catches it, not production.
- **Migrations**: `drizzle-kit push` reads the TS schema and issues the `CREATE TABLE` / `ALTER TABLE` SQL for you.

It's deliberately thin — queries look like SQL (`select`, `where`, `innerJoin`), so you're still learning SQL, not a proprietary query language. That's why I picked it over Prisma, the heavier alternative.

**2. "Defer cheap-to-reverse decisions"**
Classic senior-engineer heuristic (Bezos calls it one-way vs. two-way doors). Every decision has a reversal cost — how much work if we change our mind later:

- **SQLite → Postgres**: cheap to reverse. Drizzle abstracts the database; the swap is ~5 lines of config and a different driver. So don't burn setup time on Postgres now — decide later, when deploying forces the issue.
- **The schema shape**: expensive to reverse. Every query, seed row, agent prompt, and UI component will depend on how `threads`/`messages`/`preferences` are modeled. Changing it in Phase 3 means rewriting everything downstream.

So the rule: spend your design effort in proportion to reversal cost. That's why I wrote the schema carefully and picked the database casually.

**3. The JSON blob in `intake_forms.answers`**
The alternative was one column per question: `occasion`, `budget`, `dietary`… Two problems:

- **Forms change shape constantly.** The agency adds a question next month → `ALTER TABLE` migration. A second form version for safari trips → now what, 40 nullable columns? With JSON, every form version just stores whatever Q&A pairs it has.
- **Who reads this data?** Columns earn their keep when you *query* them (`WHERE budget > 50000`). But nobody runs SQL over intake answers — the reader is the LLM, which gets handed the whole blob as context for drafting. An LLM reads arbitrary JSON perfectly well, so rigid columns buy type safety nobody uses.

The trade-off to name in an interview: you lose DB-level validation and can't index individual answers. The escape hatch: if one field ever *does* need querying (say, budget for the proactive-suggestions phase), you promote just that field to a real column and keep the rest as JSON. That's also why `budgetUsd` lives as a column on `trips` — it *will* be queried.

### 🤖 **Claude** · 02:12

Take the Ashford intake form. It has 8 answers: occasion, travelers, dates, budget, pace, interests, avoid, dietary.

**Option A — one database column per question:**

```
intake_forms: id | occasion | travelers | dates | budget | pace | interests | avoid | dietary
```

Looks clean. But now:
- The agency adds question #9 ("celebrating anything else this year?") → you must run a schema migration to add a column.
- They make a different, shorter form for safari inquiries → half the columns are empty for those rows, and its unique questions need *more* columns.
- Two years in, the table has 40 mostly-null columns and every form change touches the database.

**Option B — what we did — one `answers` column holding JSON:**

```
intake_forms: id | clientId | tripId | answers                          | submittedAt
                                       {"occasion": "30th anniversary",
                                        "budget": "£40-50k", ...}
```

Any form, any number of questions, any version — same table, zero migrations. New question? It just appears as another key in the JSON.

**Why is B safe here?** Columns exist so the *database* can work with values — filter (`WHERE budget > 50000`), sort, index. But nothing in our app filters by intake answers. The only consumer is the drafting agent, which receives the entire blob as text in its prompt. The LLM doesn't care whether "budget" was a column or a JSON key.

**The rule underneath:** structure data as columns when the database needs to compute on it; keep it as a blob when it's just context to pass along. And it's reversible cheaply — if we later need to query one field, we lift only that field into a real column.

**Senior review — four decisions to defend:**

**1. Why is a draft a database row with `status` and `promptContext`, not just UI state?**
*The question:* "Why persist drafts at all?"
*The answer:* Three reasons. Drafts survive a page refresh (a designer steps away mid-review). The `status` lifecycle (`pending → approved/dismissed`) plus `sentBody` vs `body` gives you the eval dataset for free — acceptance rate and edit distance are *the* quality metrics for Phase 4, and you can't compute them from data you threw away. And `promptContext` stores exactly what the agent saw, so when a draft is wrong you can answer "was the context missing, or did the model ignore it?" — the first question in any production AI debugging session.

**2. Why structured output (`{body, flags}`) instead of just asking for the email text?**
Free-text output means parsing prose with regex — brittle. The schema *forces* the model to separate "the email" from "things I couldn't verify," and the `flags` array is the trust pattern made concrete: the model self-reports its own uncertainty into a channel the UI renders as "Needs your judgment." Note the mechanism: `zodOutputFormat` constrains generation server-side (the API guarantees valid JSON), it's not post-hoc parsing.

**3. Why does Approve & send write a `messages` row instead of the agent sending directly?**
The agent's output never touches the outside world. `draftReply()` can only insert `pending` rows; only the human-triggered server action creates outbound messages. That's an architectural guarantee, not a prompt instruction — a prompt saying "don't send" can fail; code with no send path can't. In the interview this is the difference between "we tell the model to be careful" and "the model structurally cannot act unsupervised."

**4. Where's the server/client component boundary and why?**
Everything is a server component except `DraftPanel` — the only interactive part (textarea state, buttons). Pages read SQLite directly with zero API routes and ship no JS for the conversation or sidebar. The subtle bit: `key={pendingDraft?.id}` on `DraftPanel` — when a new draft arrives via `revalidatePath`, the key change remounts the component so `useState(draft.body)` re-initializes. Without it, stale textarea state survives the server refresh. That's a classic React question.

One honest gap to know about: generation is a blocking server action — the designer stares at "Drafting…" for ~15–30s. Production-grade would stream the draft in. That's a deliberate v1 cut; it's on the list when we touch latency in Phase 4.

**Phase 3 — Context graph: embeddings + retrieval**

**The problem it solves:** today `getClientContext()` hands the agent a client's *entire* record. Fine at 3 clients; dead at 300 — context windows, cost, and relevance all break. Retrieval makes context *selective*: embed every fact once, then pull only what's relevant to the task at hand.

**Design:**

1. **`context_chunks` table** — one row per retrievable fact: `clientId`, `sourceType` (message | call_note | intake_answer | preference), `sourceId` (provenance, as always), `text`, `embedding` (JSON float array), `contentHash` (skip re-embedding unchanged rows).
2. **Indexing pipeline** — `indexClientContext()`: chunk each message/note/form answer, batch-embed via Voyage with `input_type: "document"`, upsert by hash. Runs as a script now; becomes a background job when data grows.
3. **Retrieval** — `retrieveContext(clientId, query, k)`: embed the query (`input_type: "query"`), brute-force cosine similarity in TypeScript over that client's chunks. *Deliberately no vector DB* — at hundreds of chunks, a linear scan is microseconds, and "I didn't add pgvector because the math said I didn't need it yet" is a great interview answer.
4. **Two consumers:**
   - A semantic search box on a new `/clients/[id]` workspace page — type "boats" and watch it surface Sarah's call note. Makes retrieval *visible* for demos.
   - `draftReply` switches from full-context to retrieved-context, and `promptContext` records which chunks were retrieved with their scores — so a bad draft is debuggable to "retrieval missed the fact" vs "model ignored it."

## 2. REST endpoint

```
POST https://api.voyageai.com/v1/embeddings
Content-Type: application/json
Authorization: Bearer $VOYAGE_API_KEY
```

Body:
```json
{
  "input": ["text one", "text two"],
  "model": "voyage-4",
  "input_type": "document",
  "truncation": true,
  "output_dimension": 1024,
  "output_dtype": "float"
}
```

- `input`: string or array of strings, **max 1,000 items** per request.
- `input_type`: `null` (default), `"query"`, or `"document"` — Voyage prepends a different internal instruction prefix to queries vs. documents to improve asymmetric retrieval (search-query embeddings vs. indexed-document embeddings). For a RAG-style pipeline: embed stored emails/notes with `input_type: "document"`, embed the user's search query with `input_type: "query"`.
- `truncation` (bool, default `true`): silently truncates any input exceeding the model's context window; set `false` to get a hard error instead.
- `output_dimension`: 256/512/1024/2048 (model-dependent).
- `output_dtype`: `float` (default), `int8`, `uint8`, `binary`, `ubinary`.
- `encoding_format`: `null` or `base64`.

Response is OpenAI-compatible: `object: "list"`, `data: [{ object: "embedding", embedding: number[], index }]`, `model`, `usage: { total_tokens }`. (The interactive reference page didn't render a literal JSON example for automated fetch, but this shape is consistent across the SDK's generated TS types and third-party provider docs — verify against the SDK's `EmbedResponse` type at implementation time.)

Source: [Embeddings API Reference](https://docs.voyageai.com/reference/embeddings-api)

## 5. Gotchas

- **Batch size**: max 1,000 strings per `input` array.
- **Per-request token budget** (sum across all inputs in the batch): reported as up to 1M tokens for lite-tier models (`voyage-4-lite`), 320K for standard models (`voyage-4`, legacy `voyage-3.5`) — treat the large/specialized-model figure as unconfirmed and check the live docs table before relying on it for `voyage-4-large`/`voyage-context-3`.
- **Per-input context window**: 32K tokens for the voyage-4 series (16K for `voyage-law-2`). Emails/call notes are almost certainly well under this.
- **Truncation default is silent**: `truncation: true` is the default — an oversized single input gets silently cut rather than erroring. Set `truncation: false` during development if you want to catch unexpectedly long inputs instead of silently losing content.
- **`input_type` matters for retrieval quality**: omitting it (leaving `null`) skips the query/document prefixing Voyage recommends for asymmetric search; for a RAG pipeline over emails/notes, explicitly set `document` at index time and `query` at search time.
- **Dimension/dtype must match at query time**: if you use `output_dimension`/`output_dtype` to shrink storage, embed queries with the *same* settings as your indexed documents — mismatched dimensions/quantization aren't comparable.
