how to take advantage of fable and use it as an orchestrator and making other work done by other models

---

### 🤖 **Claude** · 01:38

The pattern is: keep the main session on Fable, and define subagents that run on cheaper/faster models. Fable does the thinking — decomposing the task, writing precise specs, reviewing results — while Sonnet or Haiku subagents do the mechanical work in their own context windows.

**1. Main session on Fable**
`/model fable` (or `claude --model claude-fable-5`). This is your orchestrator.

**2. Define subagents with a model override**
Create files in `.claude/agents/` (project) or `~/.claude/agents/` (global). The frontmatter sets the model:

```markdown
---
name: implementer
description: Implements a precisely-specified code change. Use when the spec is already written and the work is mechanical.
model: sonnet
tools: Read, Edit, Write, Bash, Grep, Glob
---
You receive a complete spec: files to touch, exact behavior, how to verify.
Implement it faithfully. Do not redesign. Run the verification before finishing.
```

Do the same for a `researcher` on haiku (fan-out codebase searches), a `test-writer` on sonnet, etc. The built-in `Explore` and `Plan` agents already cover some of this.

**3. Drive delegation from the prompt**
Subagents don't fire on their own — you invoke them: "use the implementer agent to do steps 1–3 of the plan", or "spawn three Explore agents to map the auth, billing, and API layers in parallel." You can also override the model per call ("use the general-purpose agent on haiku"). Agents run in the background and in parallel, and `isolation: worktree` gives each one its own git worktree so parallel implementers don't stomp on each other.

**4. The economics of the split**
Fable's context is the expensive one, so protect it. The efficient loop is: Fable plans (plan mode is good here), writes each subtask as a self-contained spec — subagents start cold with none of your conversation context — fires the subagents, then reviews only their final summaries rather than their raw file dumps. Bad split: "fix the bug" (subagent redoes all the investigation). Good split: "in `src/api/client.ts:142`, change X to Y because Z; verify with `npm test -- client`."

One caveat: per your plan's guidance, spawning is the expensive path when a task is small — Fable handling a quick edit inline beats a cold-start subagent. Delegation pays off when tasks are parallel, context-heavy (huge search sweeps that would pollute your main window), or mechanical enough that Sonnet/Haiku won't fumble them.

If you ever want this programmatic rather than interactive (Fable orchestrating in code), the same `agents` concept exists in the Claude Agent SDK — but for day-to-day work, `.claude/agents/` files plus explicit delegation prompts is the whole feature.

Fair challenge. Here's the actual decision process, then where Opus fits.

**The question I ask per agent isn't "which model is smartest" — it's "what's the cheapest model whose failure mode I can live with, given that Fable reviews everything that comes back."**

- **Researcher on Haiku**: the task is grep-read-summarize. Low reasoning, high volume, often 3–4 running in parallel. Crucially, the failure mode is cheap — a shallow answer costs you one re-ask, not broken code. And you (Fable) sanity-check the summary anyway. Paying Opus prices to run `grep` is the thing this whole pattern exists to avoid. That said, if Haiku's answers on this codebase turn out flimsy, bumping that one line to `sonnet` is the fix — start cheap, promote on evidence.

- **Implementer on Sonnet**: writing code needs real capability, but the hard part (deciding *what* to build) already happened in your Fable session. Executing a precise spec is exactly the workhorse regime Sonnet is strong at, and it's the model most coding agents run on all day.

**Where's Opus?** Squeezed, honestly — and that's the interesting part. Opus sits between Sonnet and Fable, and in this setup the orchestrator slot is already taken by something stronger. So Opus isn't your default anywhere; it's your escalation tier for tasks that are genuinely hard *and* that you still want out of your main context:

- a **debugger** agent for gnarly failures (race conditions, "tests pass locally but not CI"),
- a **reviewer** agent that adversarially audits the implementer's diff before you look at it,
- an implementer *promotion*: when a spec turns out to have judgment calls in it, re-run that task with `model: opus` instead of sonnet.

The heuristic in one line: **Haiku for retrieval, Sonnet for execution, Opus for judgment you're delegating, Fable for judgment you're keeping.**

Also worth saying: for *this* repo — a learning project where the entire point is you and me walking through code together — the honest answer is most work should stay inline with Fable, and the delegation ladder matters more as a pattern you're learning than as a cost optimization here.

One interesting doc note: prompts written for older models are often *too prescriptive* for Fable and reduce quality — you state the goal and constraints and let it plan, rather than enumerating steps.

| Model | Identity | $/1M in/out |
